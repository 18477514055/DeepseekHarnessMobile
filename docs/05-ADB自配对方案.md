# ADB 自配对方案评估

> 2026-10-20 · 用户问：「打开 adb 之后它配对不了自己，怎么办？
> 是允许在设置界面加一个输入配对码吗？但配对码界面放后台可能就失效了。」

## 一、先说机制（这决定了能怎么做）

### 1.1 Android 无线调试的两个端口

```
开启「无线调试」后，设备上有两个东西在听：
  · 配对端口（pairing port）  —— 只在「使用配对码配对设备」对话框打开时存在
  · 调试端口（connect port）  —— 一直存在，但要先配对成功
```

### 1.2 配对码为什么"放后台就失效"

`adb pair` 的三方交互是：
```
PC                adbd              用户眼睛
 |-- 请求配对 ------>|                  |
 |                   |-- 显示6位码 ---->|
 |                   |                  | ← 用户把码敲进 PC
 |<-- TLS 握手 ----->|                  |
 |   （码作为握手凭据）                  |
```

**配对窗口一旦关闭（对话框消失 / 超时 1~2 分钟 / 切走 Activity），
服务端就销毁这个会话 ⇒ 码作废。**

⇒ **用户的直觉是对的**：如果让他去系统设置里看码、再切回来敲进 DSH，
    那个对话框已经没了，码必然失效。

### 1.3 但有个关键事实：**配对只需要做一次**

配对成功后，双方交换并保存长期密钥：
- 设备侧：`/data/misc/adb/adb_keys`（需要 shell 权限才能读）
- PC 侧：`~/.android/adbkey`

**之后 `adb connect <port>` 直接连，不再需要配对码。**

⇒ 所以问题不是"每次都要绕过配对"，而是**"第一次怎么配"**。

## 二、三条可行路线

### 路线 A：复用「已授权给电脑的密钥」（**推荐**）

**原理**：用户已经把手机插在电脑上、用 USB 调试授权过。
那个授权密钥就在电脑的 `~/.android/adbkey{,.pub}` 里。
如果我们把**同一对密钥**放进容器，容器就等同于"那台已授权的电脑"，
连 `127.0.0.1:<port>` **不需要配对码**。

**做法**：
1. 用户第一次用时，把电脑的 `adbkey` / `adbkey.pub` 传到手机（通过共享目录/Sendanywhere）
2. App 把它们放进容器 `~/.android/`
3. `adb connect 127.0.0.1:<port>` ⇒ 直接成功

**优点**：
- **完全不需要配对码**
- 不需要在配对窗口期做任何事
- 密钥是用户自己已有的，不引入新的信任

**缺点 / 前提**：
- 需要用户手动传一次文件（或用我们已有的「电脑↔手机」通道）
- 那个 `adbkey` 是**私钥**，会进到手机上的一个目录里 —— 要提醒风险：
  拿到它的人可以像那台电脑一样连这台手机

**★ 这条最符合"不用 ADB 就尽量不用"的原则** —— 一次性、无交互、可复用。

### 路线 B：把配对码输入框放进「配对对话框之上」的悬浮层

**原理**：不切走配对对话框，而是**在它上面叠一个输入框**。

Android 的配对对话框是系统 Activity。我们可以：
- 用 `SYSTEM_ALERT_WINDOW`（悬浮窗权限）在其上叠一个输入框
- 或者用**分屏 / 画中画**让两个界面同时可见

**问题**：
- 悬浮窗需要 `SYSTEM_ALERT_WINDOW` 特殊权限（用户要去设置里开）
- 在系统对话框上叠输入框，**焦点会被系统抢走**，键盘可能弹不出来
- 强 ROM（MIUI）可能直接禁止
- **实测成本高、可靠性差**

**结论**：理论上可行，实践中很脆弱。不推荐作为主路径。

### 路线 C：让用户用电脑 adb 帮一次（最简单）

**原理**：既然用户手边通常有电脑（本项目就是这么开发出来的），
那第一次配对干脆用电脑完成：
```
PC: adb pair 127.0.0.1:<pair_port>   ← 用户看着手机屏幕敲码
PC: adb connect 127.0.0.1:<port>     ← 配好之后
```
然后用 `adb push` 把 `adbkey` 推进容器（见路线 A）。

**优点**：最稳、零开发量
**缺点**：需要电脑在场

## 三、我的建议

**主路径 = 路线 A + C 的组合**：

| 阶段 | 做什么 | 需要谁 |
|---|---|---|
| 一次性准备 | 用电脑 `adb pair` 完成配对（路线 C，最稳） | 用户 + 电脑 |
| 把密钥搬进容器 | App 提供「导入 adbkey」按钮，从共享目录读 | App（我们能做） |
| 日常使用 | 容器内 `adb connect 127.0.0.1:<port>` 直接连 | 全自动 |

**为什么不选路线 B（悬浮窗输入配对码）**：
- 需要额外特殊权限
- 焦点问题在 MIUI 上很可能失败
- 即使做出来，也是"每次都要重新配"（因为配对码每次不同）
- 而路线 A 是**配一次、长期有效**

## 四、还需要确认的事实（待实测）

| # | 待验证 | 怎么验 |
|---|---|---|
| 1 | 配对后，容器里用同一份 adbkey 能否直接 connect | 需要真的配对一次，再在容器里 `adb connect` |
| 2 | `adb connect 127.0.0.1:<port>` 在 proot 里是否被拦 | proot 不拦 socket，理论上可以；要实测 |
| 3 | 无线调试端口每次重启都会变 | 已知会变 ⇒ 要能自动发现（读 `dumpsys adb` 或 mDNS） |
| 4 | 密钥导入后，`adbkey` 权限位要求 | 必须 600，否则 adb 拒绝 |

## 五、给用户的结论

**「配对码放后台就失效」这个判断是对的，所以不要走那条路。**

正确做法是：**配对一次（用电脑最稳），然后把密钥搬进容器，以后免配对**。
这样既避开了配对码的时间窗，也不用给 App 加悬浮窗那种高危权限。
