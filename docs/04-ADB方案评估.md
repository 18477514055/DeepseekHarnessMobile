# ADB 方案可行性评估

> 2026-10-20 · 用户提出：「能不能开容器内和容器外的 USB 无线调试用 ADB 来实现，
> 相当于在手机端实现电脑对手机的那种控制」

## 一、先说结论

**能做，但有一条硬限制，必须先讲清楚。**

## 二、原理与限制

### 2.1 ADB 的样子

```
PC ──USB/TCP──> adbd (手机上的守护进程，uid=shell, 权限极大)
                   ↑ 由系统起，不是 App 能自己起的
```

`adbd` 由 Android 系统的 `init` 拉起，**运行在 shell uid、带 SELinux 域**，
普通 App（uid=10xxx）**没有权限启动或连接它**。

### 2.2 所以「容器内调 ADB」有三条路

| 路子 | 做法 | 可行性 |
|---|---|---|
| **A. 容器内直连本机 adbd** | `adb connect 127.0.0.1:5555` | ⚠️ **要用户先开无线调试**，且 adbd 要处于 tcp 模式；容器里的 `adb` 客户端能连，但**需要配对（Android 11+ 无线调试要 pairing code）** |
| **B. 容器内起 adb 服务，PC 连进来** | 这样是**反过来的**：手机当被控端 | ❌ App 起不了 adbd |
| **C. 走 Shizuku / root** | 借别人的 shell 权限 | ❌ 需要额外装 Shizuku 或 root，违背「不依赖外部软件」 |

**⇒ 可行的只有 A，而 A 的前提是：用户手动打开「无线调试」并配对。**

### 2.3 这条路的价值

一旦连通，容器里就有一个 `adb`（可以从 Debian 源装 `adb` 包），
能做的事**非常多**：

```
adb shell input tap/swipe/text      → 真正操控手机界面
adb shell am start / pm grant       → 拉起应用、授予权限
adb shell screencap                 → 截屏
adb shell dumpsys                   → 读系统状态
adb push / pull                     → 任意文件传输
```

这确实是"电脑对手机"的完整控制能力。

### 2.4 风险（用户已明确要求：不默认开启）

- `adb shell` 是 **shell 级权限**，比任何普通 App 都高
- 一旦开启且端口暴露在局域网，**同一 Wi-Fi 下谁都能连**
- 可被用来静默安装/卸载应用、读所有应用数据、模拟任意操作

**⇒ 必须做到：**
1. **默认关闭**，用户显式开启
2. 开启时**明确警告**（不是一句"确定吗"，要列出具体风险）
3. 引导用户**自己**去系统设置里开「无线调试」
4. 提供**一键关闭** 和 **状态显示**

## 三、实施计划

### 3.1 我们这边要做的

| # | 事 |
|---|---|
| 1 | APK 里加一个「ADB 扩展」开关（默认关） |
| 2 | 开关打开时，引导用户去 **开发者选项 → 无线调试**，并展示配对步骤 |
| 3 | 容器内装 `adb` 客户端（Debian `android-tools-adb`，约 1 MB） |
| 4 | 配对成功后，`adb connect 127.0.0.1:<port>` |
| 5 | 提供一个 `dsh-adb` 包装命令，带**白名单**（见下） |
| 6 | 状态检查：`dsh-adb status` 显示连没连、能不能用 |

### 3.2 安全设计（重要）

**不做成"裸 adb"**。而是：

- `dsh-adb` 只暴露**一组白名单命令**（screencap / input / am start / pm list / dumpsys 某几项）
- 不提供 `adb shell` 裸入口（避免模型执行任意命令）
- 每次危险操作（install / uninstall / pm grant）要**用户确认**

★ 这条要跟用户确认：**是要"真·完整 adb"还是"白名单受限版"？**
  前者能力大但风险也大，后者安全但受限。

## 四、下一步

需要用户决定：
1. 是否接受"必须手动开无线调试"这个前提
2. 要完整 adb 还是白名单版
