## 二、★★ 三层问题叠加（这是这次最贵的教训）

| 层 | 现象 | 根因 | 修法 |
|---|---|---|---|
| ① 构建 | APK 430MB，assets 里是 `rootfs.tar` 1.3GB | AGP 对 `.gz` 后缀**自动解压** | 改名 `rootfs.gz.bin` |
| ② tar 解析 | `EISDIR: files/rootfs`、解析出叫 `:` 的文件 | 512 对齐未跳 / 判目录用了 sanitize 后的名字 / 符号链接当普通文件 | 重写 TarReader |
| ③ exec | `error=13 Permission denied` | **两条叠加**：SELinux 禁 exec app_data_file + **loader 缺 +x** | 降 targetSdk=28 **且** 补 `setExecutable` |

### 层③ 的详细经过（最容易误判的一层）

第一次看到的是：
```
Cannot run program ".../files/lib/proot": error=13, Permission denied
```
判断为 SELinux（正确）。降 targetSdk=28 后**仍然 13**，于是回头查，发现：
```
files/lib/libproot-loader.so  →  -rw-------（600，无执行位）
```
`stageBinaries()` 里 `copy()` 之后**没有 setExecutable**，proot 调不动 loader。
**这个报错和 SELinux 那道限制长得一模一样。**

⇒ **教训：`error=13` 必须分辨是「权限位」还是「SELinux」。**
  `File.canExecute()` 返回 true 但 exec 仍 13 ⇒ 是 SELinux；
  若 `ls -l` 显示没有 x 位 ⇒ 是权限位。两个都查，别只修一个。

## 三、★★★ `run-as` 测不出 app 内行为（这条害我最久）

```
run-as 的域：u:r:runas_app:s0        ← neverallow 豁免，能 exec files/ 里的东西
真 app 的域：u:r:untrusted_app:s0    ← targetSdk>28 时不豁免
```

这导致我在 `adb shell run-as com.dsh.mobile` 里手动测了 **七八次全部"成功"**
（`K-ok` / `M-ok` / `O-ok` / 手工最小容器 `inside-ok`），**全是假阳性**。

⇒ 必须写 `Diag.java` 从 **app 进程内部**测，才看到真实结果。
   `Diag.java` 已留在工程里（`files/diag.log`），以后遇到类似问题直接复用。

## 四、targetSdk=28 不影响能力（有对照）

**最有力证据：`com.termux` 自己就是 `targetSdk=28`**（实测 v0.119.0-beta.3）。
我们与它站在同一档位。

实测 Termux 的能力边界作参照：

```
Termux 在 $HOME 里 exec → exec-from-home-ok   ← 这正是 targetSdk=28 的红利
Termux 读 /sdcard       → READ NO            ← 它也读不了
Termux 读 /system/bin   → READ NO            ← 它也读不了
```

targetSdk 只影响**系统 API 默认行为**，不影响 Linux 层能力：

| Android 变更 | 对我们 |
|---|---|
| 10 分区存储强制 | 28 不受影响，反而更宽松 |
| 10 后台启动 activity 受限 | 28 不限制 |
| 11 软件包可见性 `<queries>` | 28 不需要声明 |
| 12 PendingIntent 显式 mutability | 已处理（`FLAG_IMMUTABLE`） |
| 13 `POST_NOTIFICATIONS` | 仍需请求，**与 targetSdk 无关** |
| 14 前台服务声明类型 | **已声明 specialUse**，与 targetSdk 无关 |
| 15/16 16KB 页对齐 | 需处理，**与 targetSdk 无关** |

**唯一代价：不能上架 Google Play**（侧载分发不受影响）。

### 5.2 为什么

打包 rootfs 时**刻意排除了 `root/.dsh`**（那是用户数据：会话、凭据、243MB）。
所以 `dshhome` 是**全新空白**的，DSH 首次启动生成默认 profile = 官方 2 个基础 bundle。

⇒ **内核是满血的**（同一个 `/opt/node` + 同一个 `@deepseek-ai/dsh` 包），
   **但插件层是空白的**。

## 六、怎么补到"满血"

### 方案 A（推荐）：首启后把开发用的 profile 一起带进去

把 Termux 那套的 `profiles/web/package.json` + `node_modules` 一起打进 rootfs 的
`dshhome/`（而不是排除它）。代价是体积涨（`node_modules` 约 100~200MB）。

### 方案 B：首启后自动装

APK 内置一个"安装插件包"的流程，首启后从内置资源装。逻辑复杂些，但体积可控。

### 方案 C：手动装

用户在界面里用插件市场/插件管理装。**这本来就是 DSH 的正常用法**，
但要联网、且每个插件都要过一遍。

★ **注意**：`dsh-mobile-adapt` 里的路径是 `link:/root/plugin-src`，
   换到 APK 后 rootfs 位置变了但**容器内路径不变**（还是 `/root/plugin-src`），
   所以这个 link 应该能直接用。

## 七、结论

**内核满血，插件层空白。**

- 现在这个 APK = **官方默认 DSH**（两个基础 bundle），能跑、能用、界面完整
- 但**不是**你现在手机上那个装了 13 个 bundle 的 DSH
- 补法明确（方案 A 最省事），缺的是**把插件层一起打包**这一步

★ 这个差距不是"降 targetSdk"造成的，是**打包时排除了 `~/.dsh`** 造成的。
  两者无关。
